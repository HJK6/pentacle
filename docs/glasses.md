# Glasses web app

The glasses entry is `/glasses` (also `/glasses/` and `/glasses.html`) on the existing Pentacle web host. Build it with `npm ci` and `npm run build:web`; serving, host profiles and `--auth tailscale` follow [the web host setup](../server/README.md). It uses that host's `/cc` websocket and shared upstream daemon connection. The daemon credential remains on the server. All scripts and fonts are served from the same origin.

The fixed 600×600 surface contains an assistant entry and Chats. The assistant label comes from live session metadata. The app calls `getAssistantBinding()`, resolves a single visible `assistant_composite` in the inventory, and checks that the bound backend's generation still matches. Missing, ambiguous or stale bindings display an unavailable state. Chats lists the existing visible session inventory, excludes assistant backends, and shows working, blocked and offline/idle indicators. Opening a chat requests its latest history using `requestStreamEvents`; live frames update the same shared transcript store.

Use Up/Down to focus list rows, Enter or Space to activate, Right to open pending questions or page forward, Left to page back, and Escape/Backspace to return. In a transcript, Up/Down scroll the latest messages. In a long question, the arrows first scroll its text while the first option is focused. Messages are newest first, with assistant text on the left and user bubbles on the right. Rich attachments and tool cards are outside this surface.

Activate Speak, then the textarea, to open the glasses' system composer. Dictated or handwritten text is committed through input/change events; activation sends the committed text. Preset quick replies use the same correlated send path and work without the device composer. The overlay shows recording, sending and sent states. A fresh message gets a fresh optimistic ID; retrying an unchanged draft retains its request and optimistic IDs. Back cancels a draft. Once submission starts, the overlay waits for its result; errors retain the draft for retry.

Question envelopes come from `promptList({producer_stream_id, open:true})`. Their option actions come from matching open notifications, joined by notification ID and exact question ID/answer value. Selecting an option submits its exact action ID and value through the existing `notificationResolve` bridge. An answer becomes green only after resolution succeeds and a readback confirms removal from the open set. Missing or ambiguous actions leave the card read-only with instructions to answer from the phone/desktop. The custom-answer row uses the same question resolution path when the envelope permits custom text. Free-text questions can use the composer directly. No server or bridge method was added.

The fonts Rajdhani, JetBrains Mono and Cinzel are copied and preloaded locally. There is no runtime CDN or Babel dependency. The home-entry structure permits a later read-only entry; no work-lanes surface or pairing endpoint is implemented here.

## Validation

Run `node scripts/run-tests.js test/glasses.test.ts test/glasses_web.test.js` for the rendered interaction and build/static-route tests. React remains external in the Node test bundles so its test scheduler uses the Node module environment; the browser build bundles React normally. `npx tsc -p tsconfig.glasses.json` checks the new files and their imported shared sources. Existing shared-source diagnostics may keep that command nonzero; compare with the same compiler/options on the base shared sources before treating them as a regression.

The browser-extension simulator and real glasses must still confirm physical rendering and system-composer behavior. A jsdom viewport assertion proves CSS constraints, not rendered text geometry. Actual device reachability and inherited tailnet authentication must be verified on the serving host and paired phone. This app does not add an authentication fallback.
